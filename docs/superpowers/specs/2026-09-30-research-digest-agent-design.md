# Research Digest Agent: 첫 공개 버전 설계

작성일: 2026-09-30

추천 부분 수정안: [PaperFlow를 참고한 추천 파이프라인](2026-09-30-recommendation-pipeline-design.md). 추천·설명·명시적 피드백의 상세 기준은 이 수정안이 우선하며 사용자 검토 전이다. 나머지 운영·전달·공개 범위는 기존 설계를 유지한다.

## 목표와 사용자

각 사용자가 자신의 컴퓨터나 서버에서 실행하는 오픈소스 CLI를 만든다. 사용자는 관심 연구 주제, 수집처, 논문 선정 기준, 팔로우할 논문·연구자, 알림 시간과 전달 채널을 설정 파일 및 안내형 CLI로 변경할 수 있다. 기본 사용 경험은 오전 9시의 짧은 논문 추천과 중요한 후속 연구에 대한 비정기 알림이다. 공개 저장소에는 개발자의 개인 설정이나 자격 증명을 포함하지 않는다.

성공 기준은 다음과 같다.

- 일일 추천은 기본 3편이며, 강한 후보가 있을 때만 최대 5편까지 늘어난다. 기준을 통과한 논문이 적으면 더 적게 보낸다.
- 각 추천에는 해당 문제가 중요한 이유, 논문의 기여와 근거, 관심 신호, 사용자 주제와의 관계, 한계, 원문 링크가 있다.
- 사용자가 팔로우한 논문 또는 연구자에 의미 있는 변화가 생겼을 때, 설정한 정책에 따라 별도 알림을 받는다.
- 같은 논문·이벤트를 여러 출처에서 발견하거나 프로그램을 재시작해도 반복 발송하지 않는다.
- 다른 연구자는 코드를 수정하지 않고 자신의 설정과 비밀정보만 준비해 사용할 수 있다.

## 구현 접근과 첫 버전 범위

첫 버전은 작은 Python 패키지와 명확한 수집·평가·전달 인터페이스로 구성한다. PaperFlow의 의미 기반 후보 검색, 관련성 기준, 다양성 재정렬, 명시적 피드백 흐름을 참고하되 중요도·기여 근거·연구계 관심을 평가하는 추천 모듈을 별도로 둔다. 전체 프로젝트 포크나 코드 재사용은 아직 하지 않았다.

포함 범위: Python 3.11 이상에서 동작하는 CLI, YAML 설정, arXiv·Hugging Face Daily Papers·선택적 Google Scholar 알림 메일 수집, Semantic Scholar를 이용한 팔로우 대상 추적, 논문 선정과 근거 기반 요약, 이메일·Slack 웹훅·Discord 웹훅·로컬 Markdown 전달, 로컬 SQLite 상태 저장, 상시 실행 명령, 설치 문서와 자동 테스트. 패키지는 GitHub 소스에서 설치할 수 있게 한다.

가입형 웹서비스, 웹 UI, Google Scholar 페이지 자동 수집이나 알림 자동 생성, 논문 PDF 전체 분석, 자동으로 관심 설정을 수정하는 추천기는 첫 버전에 포함하지 않는다. 상위 후보의 공개 HTML 본문 일부 확인과 명시적 피드백 저장·설정 변경 제안은 포함한다. alphaXiv와 deeplearn.org는 후속 수집 어댑터로 남긴다.

## 사용자 설정

`research-digest init`은 개인 설정 파일을 사용자 설정 디렉터리에 생성하고 질문을 통해 값들을 채운다. 설정 파일에는 자격 증명 값 대신 환경변수 이름만 넣는다. `research-digest doctor`는 설정 형식, 시간대, 사용 채널과 필요한 자격 증명을 검증한다. `research-digest preview`는 발송하거나 읽음 상태를 바꾸지 않고 오늘의 후보, 점수와 탈락 사유, 알림 예시를 보여준다.

설정 스키마의 주요 필드는 다음과 같다.

| 설정 | 사용자가 정하는 내용 |
| --- | --- |
| `profile` | 연구 주제별 자연어 설명, 우선순위, 포함·제외 개념, 요약 언어 |
| `sources` | arXiv 범주·검색어, Hugging Face, Scholar 메일, Semantic Scholar 사용 여부와 수집 범위 |
| `selection` | 관련성·문제 중요도·기여의 근거·관심 신호의 가중치와 최소 기준, 기본/최대 편수, 주제별 상한 |
| `schedule` | IANA 시간대, 일일 발송 시각, 후속 이벤트 확인 간격, 재시작 후 누락 실행 처리 |
| `watchlist` | DOI/arXiv/Semantic Scholar 논문 ID, Semantic Scholar 연구자 ID, 추적 이벤트와 주제 필터 |
| `notifications` | 후속 알림의 즉시/다음 다이제스트 정책, 일일 별도 알림 상한, 이메일·Slack·Discord·Markdown 채널, 요약 길이 |
| `llm` | OpenAI 호환 API 주소, 모델 이름, 키 환경변수, 요청 비용 제한 |
| `retrieval` | 의미 검색용 embedding 설정, 주제별 후보 수, 내부 평가 상한, 상위 후보 본문 일부 확인 |
| `feedback` | 명시적 응답 저장과 설정 수정 제안 사용 여부; 자동 프로필 수정은 없음 |

공개 `config.example.yaml`은 일반적인 예시만 담는다. 개인 설정 파일, 환경변수 파일, SQLite 데이터베이스 및 생성 다이제스트는 공개 저장소의 Git 추적에서 제외한다.

## 수집과 논문 선정

각 수집 어댑터는 논문 ID, 제목, 저자, 초록, 발표·수집 시각, 원문 URL, 출처, 관측 가능한 관심 신호를 공통 형식으로 반환한다. arXiv는 공식 API, Hugging Face는 Daily Papers API를 사용한다. Scholar는 사용자가 직접 설정한 알림의 메일을 IMAP으로 읽고 Scholar 웹페이지를 자동 수집하지 않는다. 한 수집처가 실패해도 나머지는 처리하며, 실패와 데이터 누락을 실행 결과에 기록한다.

동일 논문은 DOI, 버전 표시를 제거한 arXiv ID, Semantic Scholar ID 순으로 연결하고, ID가 없으면 정규화한 제목·저자 조합으로 보수적으로 중복 판정한다. 출처별 언급과 반응은 하나의 논문 기록에 보존한다. YAML 설정은 팔로우 목록을 포함한 사용자 선택의 기준 데이터이며, CLI의 `follow`·`unfollow`는 이 파일을 안전하게 수정한다. SQLite는 이미 본 논문, 수집 시각, 발송 기록, 최근 실행 상태를 저장한다. 각 수집 어댑터는 공개 API의 요청 제한을 지키고 일시적 제한에는 지수 백오프를 적용한다.

추천 흐름은 다음과 같으며 세부 규칙은 [추천 파이프라인 수정안](2026-09-30-recommendation-pipeline-design.md)에 정의한다.

1. 최근 72시간의 신규 후보를 수집하고 ID·발송 기록으로 중복을 제거한다. 중단 후 복구 수집은 최대 7일이다.
2. 넓은 연구 주제별 의미 검색으로 후보를 압축한다. 기본 주제별 10편과 관심 신호·인접 주제 추가 후보 최대 10편을 합쳐 최대 50편을 평가한다. 연구 철학은 평가 관점으로 사용하며 본인 논문 유사도에 후보를 묶지 않는다.
3. 제목·초록에서 실질적 관련성과 제외 사유를 판정한 뒤 중요도·기여 근거·관심 신호·개인 관련성을 각각 30%·30%·25%·15%로 평가한다. 측정하지 못한 관심은 `미확인`으로 표시하고 비중을 재조정한다. 유명 저자·기관·학회에 자동 가점을 주지 않는다.
4. 잠정 상위 최대 8편은 제공되는 공개 HTML 본문 일부를 확인해 근거와 한계를 보강한다. 본문이 없으면 초록 기반으로 표시한다. LLM 판단의 근거·확인 범위·관측값을 저장한다.
5. 품질 기준을 통과한 후보만 다양성 재정렬해 3~5편을 선정한다. 명시적 피드백은 저장하고 설정 수정 제안을 만들 수 있지만, 미열람을 부정적 응답으로 처리하거나 프로필을 자동 수정하지 않는다.

기본 통과 기준은 관련성·문제 중요도·기여 근거가 각각 5점 중 3점 이상이고 종합점수 3.5점 이상인 것이다. 관심 신호가 확인되지 않은 논문은 중요도와 기여 근거가 각각 4점 이상일 때만 통과한다. 통과 논문 중 기본 3편을 고르고, 종합점수가 5점 중 4점 이상인 추가 후보가 있을 때 최대 2편을 더한다. 같은 넓은 주제는 하루 2편을 넘지 않으며 문제와 기여가 거의 같은 논문은 한 편만 고른다. 임계값과 가중치는 설정에서 바꿀 수 있다. 수치 점수는 추천 우선순위를 위한 내부 기준이며 실제 학술적 영향력을 확정하는 표현으로 사용하지 않는다.

일일 메시지는 가장 우선하는 1편을 `정독 후보`로, 나머지를 `빠르게 훑어볼 후보`로 구분한다. 각 논문은 읽을 가치, 핵심 기여·근거, 관측된 관심과 한계, 사용자 주제와의 관계, 읽으며 확인할 질문, 원문 링크를 짧게 제시한다. `초록 기반` 또는 `본문 일부 확인`을 표시하고 확인하지 않은 실험 수치나 결론을 만들어내지 않는다.

## 팔로우와 이벤트 알림

사용자는 `research-digest follow paper <ID>` 또는 `research-digest follow author <ID>`로 팔로우 목록을 바꾸거나 YAML에서 직접 수정한다. 첫 버전의 이벤트는 `연구자의 새 논문`과 `팔로우한 논문을 인용한 새 논문`이다. Semantic Scholar Academic Graph API의 연구자 논문·논문 인용 데이터를 우선 사용하고, 사용자가 Scholar 메일을 연결했다면 해당 알림도 후보로 합친다. API나 Scholar의 색인 지연 때문에 이벤트 알림은 논문 발행 시각이 아닌 발견 시각을 기준으로 한다.

새 인용은 자동으로 후속 연구로 간주하지 않는다. 초록에서 같은 문제를 발전시키는지 평가하고 설정된 관련성·중요도 기준을 통과한 경우만 알린다. 연구자의 새 논문도 사용자가 `topic_filter`를 켰다면 해당 연구 주제에 맞는 것만 알린다. 사용자는 이벤트별로 `immediate` 또는 `next_digest`를 정할 수 있다. 즉시 알림은 기본적으로 하루 최대 3건이며 초과분은 다음 다이제스트에 묶는다. 같은 논문이 일일 추천과 이벤트 양쪽에 들어가면 한 번만 전달한다. 고유 이벤트 ID와 발송 기록으로 재시작 후 중복 발송을 억제한다.

## 실행, 전달, 오류 처리

CLI는 `init`, `doctor`, `preview`, `follow`, `unfollow`, `feedback`, `run --once`, `serve`를 제공한다. `serve`는 설정된 시간대에 일일 다이제스트를 보내고, 설정된 간격으로 팔로우 이벤트를 검사한다. 시작 시 마지막 성공 실행을 확인해 누락된 일일 발송이 있다면 하나의 복구 다이제스트로 묶어 최대 5편만 보낸다. 설정 파일의 변경은 다음 검사 주기에 반영한다. 정확한 시각 발송에는 상시 실행되는 컴퓨터 또는 서버가 필요하다. 첫 버전은 Docker Compose와 로컬 실행 예시를 제공한다.

발송기는 이메일 SMTP, Slack 웹훅, Discord 웹훅, 로컬 Markdown 파일을 지원한다. 여러 채널을 함께 고를 수 있다. 네트워크 또는 발송 오류는 제한된 재시도 후 기록하고, 성공한 채널과 실패한 채널을 구분해 재시도한다. `preview`와 테스트에서는 외부 발송을 하지 않는다. 자격 증명은 환경변수로 전달하고 로그·오류 메시지에 포함하지 않는다. 사용자는 OpenAI 호환 LLM 제공자를 직접 지정하고 해당 제공자의 비용·개인정보 조건을 확인할 수 있다.

## 공개 저장소와 검증

저장소에는 MIT 라이선스, README의 빠른 시작, 설정 필드 설명, Scholar 메일 연결 안내, 실행 방식별 안내, 예시 다이제스트, 기여 안내, GitHub Actions CI를 둔다. CI는 Python 3.11·3.12에서 단위·통합 테스트를 실행한다. 발송 자격 증명이 없는 환경에서도 샘플 데이터로 `preview`를 실행할 수 있어야 한다.

핵심 검증은 네 출처의 표본 데이터 정규화, DOI/arXiv 중복 제거, 설정 검증, 연구 주제·점수·일일 상한, 후속 이벤트 판정, 시간대와 재시작 복구, 채널별 발송·재시도와 비밀정보 비노출을 포함한다. 실제 API·IMAP·SMTP를 쓰는 선택적 스모크 테스트는 별도 명령으로 실행한다. 공개 전에는 샘플 설정만으로 설치부터 미리보기까지 재현하고, 개인 설정이나 비밀정보가 Git에 포함되지 않았음을 확인한다.
